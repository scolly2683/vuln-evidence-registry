Preconditions from Prose

How we turn the sentences in vulnerability advisories into machine-readable answers to one question: does this CVE actually apply to this deployment? Walked through on three real CVEs.

The problem

When a vulnerability (a CVE) is published, the facts that decide whether it matters to you usually arrive as ordinary sentences, not as data. In one measured month, 67% of new CVEs had no machine-readable product identification (no CPE record) at the moment of disclosure — and the conditions that gate exploitability almost never get structured data at all.

Those conditions — we call them preconditions — are things like: a feature that must be switched on, a specific function the application must call, a deployment path that must exist. Two organisations running the same version of the same software can be in completely different positions: one exploitable today, one not exposed at all. If nobody reads the sentence that says so, both get the same ticket.

This project extracts that information into a structured, tested form. Every example below is a real advisory, quoted character-for-character and verified against its official source.

How an advisory gets read

  1. 1

    Flag candidate sentences

    A simple keyword scanner marks every sentence that might state a precondition. It deliberately over-flags — it is a net, not a judge.

  2. 2

    Review each candidate

    A reviewer decides: genuine precondition, or false match? Every verdict must cite the exact sentence it rests on — no citation, no verdict.

  3. 3

    Keep everything, pin everything

    Genuine preconditions become structured records. False matches are not discarded — fix history is filed as remediation notes, flaw description as general notes. The whole worked example becomes a permanent regression test.

Case 1 · Log4Shell — one sentence carrying everything

CVE-2021-44228Apache Log4j2 source: NVD

Advisory text, verbatim — highlights are the flagged candidates

1Apache Log4j2 2.0-beta9 through 2.15.0 (excluding security releases 2.12.2, 2.12.3, and 2.3.1) JNDI features used in configuration, log messages, and parameters do not protect against attacker controlled LDAP and other JNDI related endpoints. 2An attacker who can control log messages or log message parameters can execute arbitrary code loaded from LDAP servers when message lookup substitution is enabled. 3From log4j 2.15.0, this behavior has been disabled by default. 4From version 2.16.0 (along with 2.12.2, 2.12.3, and 2.3.1), this functionality has been completely removed. Note that this vulnerability is specific to log4j-core and does not affect log4net, log4cxx, or other Apache Logging Services projects.

  1. 1
    False match

    Describes the flaw itself — what is broken and where — not a condition your deployment must meet. Kept as a general note.

  2. 2
    Genuine

    Three real preconditions packed into one sentence: the configuration toggle (“when message lookup substitution is enabled”), attacker-influenced input (“who can control log messages…”), and outbound reachability (“code loaded from LDAP servers”).

  3. 3
    Reclassified → vendor fix

    Fix history, not a condition on the target — filed as a remediation note (and flagged as a partial fix: 2.15.0 was later bypassed as CVE-2021-45046).

  4. 4
    Reclassified → vendor fix

    The real fix boundary — this sentence also feeds the version-range extraction (fixed: 2.16.0, plus the three backport releases).

What lands in the structured record

  • 3 preconditions — message-lookup substitution enabled (on by default), attacker-influenced log input, outbound JNDI/LDAP reachability. All three must hold.
  • 2 remediation notes (vendor fix) and 1 general note — nothing from the advisory is thrown away.
  • Version range — 2.0-beta9 → fixed 2.16.0, excluding backports 2.12.2, 2.12.3, 2.3.1.

The takeaway: “one sentence = one precondition” is the wrong mental model. A sentence is evidence for preconditions — sometimes several at once.

Case 2 · Drupalgeddon2 — zero preconditions, on purpose

CVE-2018-7600Drupal core source: NVD

Advisory text, verbatim

1Drupal before 7.58, 8.x before 8.3.9, 8.4.x before 8.4.6, and 8.5.x before 8.5.1 allows remote attackers to execute arbitrary code because of an issue affecting multiple subsystems with default or common module configurations.

  1. 1
    False match

    The scanner flagged this on the word “configurations” — but read the sentence: default or common configurations are affected. That is the opposite of a precondition. It is the evidence that nothing gates this CVE.

What lands in the structured record

  • Preconditions: none — recorded as an explicit empty list, a deliberate claim, not missing data. Running an affected version is enough to be exploitable.
  • Version fixes per branch — 7.58, 8.3.9, 8.4.6, 8.5.1: a shape a single “fixed version” field cannot express, so it is carried in notes.

The takeaway: for a CVE like this, any time spent asking “does it apply to us?” is time lost. The record says so explicitly, so triage can skip straight to “patch it.”

Case 3 · Rails Action View — the advisory that doesn’t say

CVE-2019-5418Action View (Ruby on Rails) source: NVD

Advisory text, verbatim — nothing flagged

There is a File Content Disclosure vulnerability in Action View <5.2.2.1, <5.1.6.2, <5.0.7.2, <4.2.11.1 and v3 where specially crafted accept headers can cause contents of arbitrary files on the target system's filesystem to be exposed.

The sentence that isn’t there: only applications that call render file: in a controller are actually affected. That fact appears in the Rails release announcement — but not in this advisory text. No tool reading only this text can recover it.

What lands in the structured record

  • Preconditions: none stated — also an empty list, but with notes marking it as the opposite claim to Drupalgeddon2’s: a precondition truly exists, the text just never states it.

The takeaway: this is the honest ceiling of advisory-text-only extraction, pinned as a permanent test case. When the text under-specifies, the record says “none stated” — it never guesses.

What this doesn’t do yet

  • Identity resolution

    Turning “GNU Bash” or “the PyYAML library” into a formal product identifier (CPE or package URL) is a lookup-against-a-dictionary problem, and is not attempted here at all yet.

  • Keyword gaps — the jwt-go miss

    The scanner produces zero candidates for CVE-2020-26160 (jwt-go), whose real precondition — “a service that lacks its own audience check” — contains none of the current keywords. This miss is pinned as a failing-by-design test, so fixing it will be a visible change, never a silent one.

  • Candidates are leads, not verdicts

    Keyword flagging is a starting point for review. The review step shown above was performed by hand; an automated review call exists in the code but has not yet been exercised against the live API.
